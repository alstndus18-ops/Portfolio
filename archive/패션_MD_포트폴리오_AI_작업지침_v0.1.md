# 패션 MD 포트폴리오 AI 작업 지침

## 문서 목적

이 문서는 패션 MD 또는 관련 직무 지원자를 위한 웹 포트폴리오 프로젝트의 공통 기준이다. AI는 이 문서를 먼저 읽고, 사용자에게 불필요하게 기술적인 선택을 떠넘기지 않으면서도 실제 서비스처럼 설득력 있는 결과물을 만든다.

이 문서는 계속 보완한다. 확정되지 않은 항목은 추측으로 채우지 말고, `확인 필요`로 표시하거나 짧게 질문한다.

## 프로젝트의 핵심 방향

만들 대상은 단순한 자기소개 페이지가 아니라, 지원자가 MD 관점으로 문제를 발견하고 제품을 기획하며 화면과 정보 구조를 설계할 수 있음을 보여 주는 웹 포트폴리오다.

현재 예시 프로젝트는 다음과 같다.

> 쇼핑몰 URL을 기준으로 유사 경쟁 후보를 제안하고, 후보별 BEST 상품과 가격을 출처 및 마지막 확인 시각과 함께 비교하는 MD 리서치 도구

이 프로젝트는 다음 역량을 보여 주어야 한다.

- 여러 쇼핑몰의 상품군과 가격대를 비교해야 하는 MD의 실제 업무 맥락 이해
- 기준 쇼핑몰과 경쟁 후보를 구분하고, 후보 선정 근거를 설명하는 기획력
- 상품 카드, 가격, 할인 여부, 카테고리, 출처, 확인 시각을 우선순위 있게 보여 주는 정보 설계력
- URL 입력, 후보 선택 및 제외, 상품 비교, 재시도 등 사용자 흐름 설계력
- 데이터가 부족하거나 수집에 실패했을 때도 정직하게 안내하는 신뢰성 있는 UX
- 데스크톱과 모바일에서 모두 읽기 쉬운 시각적 완성도

## 반드시 지킬 원칙

### 사실성과 출처

- 실제로 확인하지 않은 상품, 가격, 리뷰 수, 판매량, 시장 점유율, 고객 반응을 사실처럼 만들지 않는다.
- 데모 데이터는 `샘플`, `데모`, `미확인`처럼 분명히 표시한다.
- 가격, BEST 순위, 상품 정보는 바뀔 수 있으므로 출처 링크와 마지막 확인 시각을 함께 설계한다.
- 후보 쇼핑몰은 자동 확정 경쟁사로 단정하지 않는다. 카테고리, 가격대, 키워드 등 선정 근거를 보이고 사용자가 포함 또는 제외할 수 있게 한다.
- 실제 데이터 수집을 구현할 때는 공개 페이지와 해당 사이트의 이용 조건 및 `robots.txt`를 존중한다. 로그인, 차단, 접근 제한을 우회하지 않는다.

### 포트폴리오의 정직성

- 지원자가 한 일, AI 도움을 받은 일, 데모 범위를 구분할 수 있게 한다.
- 작동하지 않는 기능을 작동하는 것처럼 보이게 만들지 않는다.
- 백엔드나 실시간 수집이 없다면 정적 프로토타입 또는 데모라고 명시한다.
- 포트폴리오의 목표는 화려한 효과가 아니라 문제 정의, 판단 근거, 사용자 경험, 구현 품질을 보여 주는 것이다.

## 디자인 방향

### 지향점

- 패션 감각은 있으되, 패션 브랜드 광고 페이지가 아니라 반복 사용 가능한 MD 리서치 도구처럼 보이게 한다.
- 화면은 차분하고 신뢰감 있으며, 비교와 스캔이 쉬워야 한다.
- 상품 이미지와 가격 정보가 주인공이되, 출처와 상태 정보가 묻히지 않게 한다.
- 데이터가 많은 화면은 무조건 카드로 쪼개지 않는다. 표, 비교 행, 필터, 상태 표시 등 목적에 맞는 구조를 사용한다.
- 여백, 타이포그래피, 색, 아이콘, 테두리, 상태 색상을 일관된 시스템으로 관리한다.

### 피해야 할 AI스러운 표현

- 근거 없는 통계, 고객 수, 만족도, 후기, 성과 수치
- 보라색 그라데이션, 유리 질감, 과도하게 둥근 카드, 장식용 블롭을 기본값처럼 쓰는 것
- 모든 영역을 같은 크기의 카드 3개로 나누는 반복적 구성
- 기능 없는 탭, 필터, 버튼, 배지
- 지나치게 작은 저대비 텍스트, 모바일에서 가로 스크롤이 필요한 핵심 기능
- 화면의 목적과 관계없는 3D, 패럴랙스, 과도한 애니메이션
- 상품 데이터가 부족할 때 실제 상품처럼 보이는 임의 이미지나 수치를 채우는 것

### 권장 화면 구조

1. **분석 시작 화면**: 서비스 설명, URL 입력, 지원 범위 및 데모 안내
2. **분석 상태 화면**: 분석 중, 완료, 부분 성공, 실패, 재시도 상태를 명확히 구분
3. **기준 쇼핑몰 요약**: 쇼핑몰명, 대표 카테고리, 확인 가능 범위, 마지막 확인 시각
4. **경쟁 후보 검토**: 후보별 선정 근거, 유사도 설명, 포함·제외 조작
5. **BEST 상품 비교**: 상품 이미지, 상품명, 카테고리, 현재가/할인가, 순위 또는 BEST 표기, 출처 링크, 확인 시각
6. **예외 및 신뢰 정보**: 미수집, 오래된 데이터, 지원하지 않는 도메인, 오류 이유와 다음 행동 안내
7. **포트폴리오 설명 영역**: 문제 정의, 사용자 흐름, 디자인 결정, 데모 범위, 향후 개선점

## 작업 방식

### Codex를 기본 작업 공간으로 사용한다

- 이 프로젝트에 관련된 기획 문서, 이미지, 코드, 화면 캡처, 테스트 결과는 한 프로젝트 폴더 안에 둔다.
- AI와 새 채팅을 시작해도 판단 기준이 유지되도록 중요한 결정은 파일로 남긴다.
- GitHub 저장소를 사용해 다른 PC에서도 프로젝트를 이어갈 수 있게 한다.
- 대화 기록만 믿지 않는다. 프로젝트 파일이 최종 기준이다.

### 권장 프로젝트 구조

```text
fashion-md-portfolio/
├─ README.md                         # 프로젝트 소개와 실행 방법
├─ PORTFOLIO_BRIEF.md                # 목표 직무, 보여 줄 역량, 핵심 스토리
├─ DESIGN.md                         # 색, 폰트, 여백, 컴포넌트, 금지 요소
├─ DECISIONS.md                      # 주요 결정과 이유
├─ research/                         # 채용공고, 레퍼런스, 출처 기록
├─ assets/                           # 직접 사용 권한이 있는 이미지와 아이콘
├─ docs/                             # 기획안, 사용자 흐름, 화면 설명
├─ src/ 또는 사이트 파일/
└─ tests/                            # 가능한 경우 사용자 흐름 테스트
```

### AI가 작업을 시작할 때의 순서

1. `README.md`, `PORTFOLIO_BRIEF.md`, `DESIGN.md`, `DECISIONS.md`가 있으면 먼저 읽는다.
2. 현재 목표가 기획, 화면 구조, 구현, 검토, 테스트 중 무엇인지 확인한다.
3. 이미 정해진 디자인 시스템과 데모 범위를 지킨다.
4. 불분명한 사실은 만들어 내지 않고 확인 필요 항목으로 남긴다.
5. 작업 후에는 바뀐 파일, 확인한 동작, 남은 제한 사항을 짧게 정리한다.

## 사용할 스킬 후보

AI는 아래 스킬이 설치되어 있는지 먼저 확인한다. 설치되어 있지 않다면 없는 스킬을 사용했다고 주장하지 않으며, 사용자의 승인 없이 외부 스킬이나 패키지를 설치하지 않는다.

### 기본 후보

| 역할 | 후보 스킬 | 사용할 때 |
|---|---|---|
| 화면 구현 | Frontend Design | 화면·컴포넌트·대시보드·반응형 UI를 새로 만들거나 크게 개선할 때 |
| 디자인 일관성 | DESIGN.md | 화면이 늘어나도 색·폰트·여백·컴포넌트 규칙을 유지할 때 |
| AI스러운 디자인 제거 | Avoid AI Design | 완성 화면이 흔한 AI UI처럼 보이는지 점검하고 다듬을 때 |
| 실제 동작 검증 | Web Application Testing | URL 입력, 후보 선택, 비교, 오류·재시도 흐름을 브라우저에서 확인할 때 |
| 접근성 점검 | Accessibility Compliance | 키보드, 색 대비, 이미지 설명, 포커스, 모바일 터치 영역을 점검할 때 |
| 화면 비평 | Design Critique | 캡처된 화면 또는 실행 중인 화면을 기준으로 우선순위 있는 개선안을 만들 때 |

### 기획 단계에서 추가할 후보

| 역할 | 후보 스킬 | 사용할 때 |
|---|---|---|
| 디자인 브리프 | Design Brief | 사용자, 문제, 화면 분위기, 제약을 확정하기 전 |
| 정보 구조 | Information Architecture | 화면, 메뉴, 페이지, 비교 흐름을 정리할 때 |
| 와이어프레임 | ASCII Wireframes | 코딩 전 서로 다른 레이아웃을 빠르게 비교할 때 |
| 제품 기획 | Product Management | MVP 범위, 요구사항, 사용자 스토리, 우선순위를 정리할 때 |
| UX 리서치 | UX Research | 실제 MD 또는 잠재 사용자에게 받을 피드백을 설계할 때 |

### 설치 선택 기준

- 화면을 **만드는 기준**은 `Frontend Design` 또는 `UI UX Pro Max` 중 하나를 우선 선택한다. 둘을 동시에 강하게 적용하지 않는다.
- 결과물을 **다듬는 기준**은 `Avoid AI Design` 또는 `Anti Slop` 중 하나를 우선 선택한다.
- 실제 서비스처럼 보이려면 `Web Application Testing`과 `Accessibility Compliance`가 유용하다.
- `Design Brief`, `Information Architecture`, `ASCII Wireframes`는 친구가 기획 과정을 직접 보여 주고 싶을 때 추가한다.
- 모든 스킬을 한 번에 설치하지 않는다. 현재 과제에 필요한 소수만 사용한다.

## 디자인과 구현의 완료 기준

다음 항목을 충족하기 전에는 완료라고 말하지 않는다.

- 첫 화면에서 서비스 목적과 사용자가 할 일이 빠르게 이해된다.
- URL 입력부터 후보 검토, 상품 비교까지 흐름이 자연스럽다.
- 로딩, 빈 결과, 부분 성공, 실패, 재시도, 오래된 데이터 상태가 설계되어 있다.
- 상품·가격·순위 정보는 출처 또는 데모 표기가 분명하다.
- 데스크톱과 모바일에서 글자, 상품 카드, 표, 필터, 버튼이 겹치거나 잘리지 않는다.
- 키보드만으로 핵심 조작이 가능하고 포커스가 보인다.
- 색만으로 상태를 구분하지 않으며, 이미지에는 적절한 대체 텍스트가 있다.
- 디자인이 프로젝트의 목적에 맞고, 장식이 정보 이해를 방해하지 않는다.
- 핵심 사용자 흐름을 실제로 실행하거나 검토했으며, 확인하지 못한 부분은 미검증이라고 적는다.

## 포트폴리오에 함께 보여 줄 내용

- 문제: MD가 왜 반복적으로 경쟁 쇼핑몰을 조사하는가
- 사용자: 어떤 MD가 어떤 상황에서 사용하는가
- 해결 방식: 후보를 단정하지 않고 근거와 선택권을 제공한 이유
- 정보 설계: 상품 카드와 비교 화면에서 무엇을 우선 보여 주었는가
- 신뢰 설계: 출처, 확인 시각, 미확인 값, 실패 상태를 어떻게 다루었는가
- 디자인 결정: 왜 패션 광고형이 아니라 리서치 도구형 UI를 선택했는가
- 데모 범위: 정적 프로토타입인지, 실제 연결 기능이 있는지
- 개선 계획: 지원 쇼핑몰 확대, 저장·비교 이력, 필터, 데이터 갱신 등

## 앞으로 추가할 항목

- [ ] 친구의 실제 목표 직무와 경력 수준
- [ ] 사용할 기술 방식: 순수 HTML/CSS/JS 또는 React 등
- [ ] 참고할 패션 브랜드 및 경쟁 서비스
- [ ] 실제로 설치할 스킬과 설치 위치
- [ ] 포트폴리오의 최종 형식: 웹사이트, PDF, 발표 자료, 노션 등
- [ ] GitHub와 클라우드 폴더 운영 방식
- [ ] 채용공고 분석, 자소서, 면접 준비와 연결하는 방법
- [ ] 데이터 수집을 실제로 구현할지, 정적 데모로 유지할지

```text
이 프로젝트 폴더의 README.md, PORTFOLIO_BRIEF.md, DESIGN.md, DECISIONS.md를 먼저 읽어줘.

작업 후에는 변경한 파일, 검증한 항목, 아직 확인하지 못한 제한 사항을 정리해줘.
```
